# Приложение. Структура базы данных

Ниже приведена новая структура базы данных для `MVP` проекта SmartTeach. Документ полностью заменяет предыдущий черновик и опирается только на согласованные решения по текущей версии продукта.

База данных проектируется под `PostgreSQL`, а прикладной слой доступа к данным предполагается через `Prisma`.

## Общие принципы

- Для основных сущностей используется первичный ключ `id` типа `UUID`.
- Все основные записи содержат поля аудита `created_at` и `updated_at`, если это уместно для сущности.
- Связи многие-ко-многим оформляются отдельными таблицами-связками.
- Файлы хранятся во внешнем объектном хранилище `MinIO`, а в БД сохраняются только метаданные.
- Основой предметной области является сущность группы `groups`.
- `Course` и `Class` в `MVP` не выделяются в отдельные режимы и не влияют на схему.
- Глобальные роли сервиса, `OAuth`, уведомления и логи модерации в `MVP` не входят.

## 1. Пользователи и авторизация

### Таблица `users`

Основная таблица аккаунтов пользователей.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `UUID` | Первичный ключ пользователя. |
| `email` | `VARCHAR(255)` | Уникальный email пользователя, используется для входа в систему. |
| `password_hash` | `VARCHAR(255)` | Хэш пароля пользователя. Пароль в открытом виде не хранится. |
| `display_name` | `VARCHAR(100)` | Имя пользователя, которое отображается в интерфейсе. |
| `bio` | `TEXT` | Краткое описание пользователя. Может быть `NULL`. |
| `avatar_file_id` | `UUID` | Ссылка на файл аватара из таблицы `files`. Может быть `NULL`. |
| `created_at` | `TIMESTAMPTZ` | Дата и время создания аккаунта. |
| `updated_at` | `TIMESTAMPTZ` | Дата и время последнего обновления профиля. |

Основные ограничения:

- `email` должен быть уникальным.
- `avatar_file_id` ссылается на `files.id`.
- `email` рекомендуется хранить в нормализованном виде, например в lowercase.

### Таблица `sessions`

Хранит пользовательские сессии и `refresh token` для безопасного продления авторизации и выхода с устройств.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `UUID` | Первичный ключ сессии. |
| `user_id` | `UUID` | Ссылка на пользователя из таблицы `users`. |
| `refresh_token_hash` | `VARCHAR(255)` | Хэш `refresh token`. Сам токен в открытом виде не хранится. |
| `user_agent` | `TEXT` | Информация о браузере или устройстве пользователя. Может быть `NULL`. |
| `ip_address` | `INET` | IP-адрес пользователя. Может быть `NULL`. |
| `last_used_at` | `TIMESTAMPTZ` | Время последнего использования сессии. Может быть `NULL`. |
| `expires_at` | `TIMESTAMPTZ` | Время окончания действия сессии. |
| `revoked_at` | `TIMESTAMPTZ` | Время отзыва сессии. Может быть `NULL`. |
| `created_at` | `TIMESTAMPTZ` | Дата и время создания сессии. |

Основные ограничения:

- `user_id` ссылается на `users.id`.
- Для частых выборок нужны индексы по `user_id` и `expires_at`.

## 2. Файлы

### Таблица `files`

Единая таблица метаданных файлов для аватаров, вложений уроков, заданий, сдач и сообщений.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `UUID` | Первичный ключ файла. |
| `storage_key` | `VARCHAR(255)` | Уникальный ключ файла в `MinIO`. |
| `original_name` | `VARCHAR(255)` | Исходное имя файла при загрузке. |
| `mime_type` | `VARCHAR(100)` | MIME-тип файла. |
| `size_bytes` | `BIGINT` | Размер файла в байтах. |
| `uploaded_by_user_id` | `UUID` | Пользователь, который загрузил файл. |
| `created_at` | `TIMESTAMPTZ` | Дата и время загрузки файла. |
| `deleted_at` | `TIMESTAMPTZ` | Время мягкого удаления файла. Может быть `NULL`. |

Основные ограничения:

- `storage_key` должен быть уникальным.
- `uploaded_by_user_id` ссылается на `users.id`.

## 3. Группы

### Таблица `groups`

Центральная сущность системы. Все учебные и групповые сценарии строятся вокруг этой таблицы.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `UUID` | Первичный ключ группы. |
| `code` | `VARCHAR(20)` | Уникальный короткий код группы для быстрого поиска. Генерируется автоматически. |
| `name` | `VARCHAR(150)` | Название группы. |
| `description` | `TEXT` | Описание группы, целей или правил участия. Может быть `NULL`. |
| `owner_id` | `UUID` | Пользователь-владелец группы. |
| `access_mode` | `ENUM` | Режим вступления: `OPEN`, `BY_REQUEST`, `CLOSED`. |
| `status` | `ENUM` | Состояние группы: `ACTIVE`, `ARCHIVED`, `DELETED`. |
| `created_at` | `TIMESTAMPTZ` | Дата и время создания группы. |
| `updated_at` | `TIMESTAMPTZ` | Дата и время последнего обновления группы. |
| `archived_at` | `TIMESTAMPTZ` | Время отправки группы в архив. Может быть `NULL`. |
| `deleted_at` | `TIMESTAMPTZ` | Время мягкого удаления группы. Может быть `NULL`. |

Основные ограничения:

- `code` должен быть уникальным.
- `owner_id` ссылается на `users.id`.
- Для частых выборок нужны индексы по `owner_id`, `status` и `code`.

### Таблица `group_settings`

Отдельная таблица настроек группы. Связь с `groups` строго `1:1`.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `group_id` | `UUID` | Идентификатор группы. Одновременно первичный ключ и внешний ключ на `groups.id`. |
| `chat_enabled` | `BOOLEAN` | Включены ли групповые чаты. |
| `lessons_enabled` | `BOOLEAN` | Включены ли уроки. |
| `assignments_enabled` | `BOOLEAN` | Включены ли задания. |
| `schedule_enabled` | `BOOLEAN` | Включено ли расписание. |
| `created_at` | `TIMESTAMPTZ` | Дата и время создания строки настроек. |
| `updated_at` | `TIMESTAMPTZ` | Дата и время последнего обновления настроек. |

Основные правила:

- У каждой группы должна существовать ровно одна строка в `group_settings`.
- Строка создается одновременно с созданием группы.

### Таблица `group_members`

Хранит текущий состав участников группы и их роли.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `group_id` | `UUID` | Ссылка на группу из таблицы `groups`. |
| `user_id` | `UUID` | Ссылка на пользователя из таблицы `users`. |
| `role` | `ENUM` | Роль участника в группе: `OWNER`, `ADMIN`, `USER`. |
| `joined_at` | `TIMESTAMPTZ` | Дата и время вступления в группу. |
| `updated_at` | `TIMESTAMPTZ` | Дата и время последнего изменения записи, например при смене роли. |

Для таблицы `group_members` используется составной первичный ключ `group_id + user_id`.

Основные правила:

- В таблице хранятся только текущие участники группы.
- Пользователь из `groups.owner_id` обязательно должен присутствовать в `group_members` с ролью `OWNER`.
- В одной группе должен быть ровно один `OWNER`.

### Таблица `group_join_requests`

Хранит заявки на вступление в группы с режимом доступа `BY_REQUEST`.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `UUID` | Первичный ключ заявки. |
| `group_id` | `UUID` | В какую группу подана заявка. |
| `user_id` | `UUID` | Кто подал заявку. |
| `status` | `ENUM` | Статус заявки: `PENDING`, `APPROVED`, `REJECTED`. |
| `reviewed_by_user_id` | `UUID` | Кто рассмотрел заявку. Может быть `NULL`. |
| `reviewed_at` | `TIMESTAMPTZ` | Когда заявка была рассмотрена. Может быть `NULL`. |
| `created_at` | `TIMESTAMPTZ` | Когда заявка была создана. |
| `updated_at` | `TIMESTAMPTZ` | Когда заявка последний раз менялась. |

Основные правила:

- Для одной пары `group_id + user_id` не должно существовать более одной активной заявки со статусом `PENDING`.
- Если заявка переводится в `APPROVED`, создается запись в `group_members`.
- Для групп с режимом `OPEN` заявки не нужны.
- Для групп с режимом `CLOSED` пользователь не может подать заявку сам.

## 4. Учебные сущности

### Таблица `lessons`

Хранит уроки, созданные внутри группы.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `UUID` | Первичный ключ урока. |
| `group_id` | `UUID` | Группа, внутри которой создан урок. |
| `title` | `VARCHAR(200)` | Название урока. |
| `content` | `TEXT` | Основной текст урока: описание, материалы, инструкции. Может быть `NULL`. |
| `status` | `ENUM` | Статус урока: `DRAFT`, `PUBLISHED`, `ARCHIVED`. |
| `sort_order` | `INTEGER` | Порядок урока внутри группы. |
| `starts_at` | `TIMESTAMPTZ` | Плановое время начала урока. Может быть `NULL`. |
| `ends_at` | `TIMESTAMPTZ` | Плановое время окончания урока. Может быть `NULL`. |
| `published_at` | `TIMESTAMPTZ` | Время публикации урока. Может быть `NULL`. |
| `archived_at` | `TIMESTAMPTZ` | Время архивирования урока. Может быть `NULL`. |
| `created_by_user_id` | `UUID` | Пользователь, создавший урок. |
| `created_at` | `TIMESTAMPTZ` | Дата и время создания урока. |
| `updated_at` | `TIMESTAMPTZ` | Дата и время последнего обновления урока. |

Основные правила:

- Уроки можно создавать только если в `group_settings` включен `lessons_enabled`.
- Для порядка отображения используется `sort_order`, а не только дата создания.

### Таблица `lesson_files`

Связка между уроками и прикрепленными файлами.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `lesson_id` | `UUID` | Ссылка на урок из таблицы `lessons`. |
| `file_id` | `UUID` | Ссылка на файл из таблицы `files`. |
| `sort_order` | `INTEGER` | Порядок файла внутри урока. |
| `attached_at` | `TIMESTAMPTZ` | Время прикрепления файла. |

Для таблицы `lesson_files` рекомендуется использовать составной первичный ключ `lesson_id + file_id`.

### Таблица `assignments`

Хранит задания группы. Задание может быть как самостоятельным, так и привязанным к конкретному уроку.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `UUID` | Первичный ключ задания. |
| `group_id` | `UUID` | Группа, в которой создано задание. |
| `lesson_id` | `UUID` | Ссылка на урок, если задание относится к конкретному уроку. Может быть `NULL`. |
| `title` | `VARCHAR(200)` | Название задания. |
| `content` | `TEXT` | Полное условие задания. Может быть `NULL`. |
| `status` | `ENUM` | Статус задания: `DRAFT`, `PUBLISHED`, `ARCHIVED`. |
| `due_at` | `TIMESTAMPTZ` | Дедлайн сдачи. Может быть `NULL`. |
| `max_score` | `INTEGER` | Максимальный балл за задание. Может быть `NULL`. |
| `published_at` | `TIMESTAMPTZ` | Время публикации задания. Может быть `NULL`. |
| `archived_at` | `TIMESTAMPTZ` | Время архивирования задания. Может быть `NULL`. |
| `created_by_user_id` | `UUID` | Пользователь, создавший задание. |
| `created_at` | `TIMESTAMPTZ` | Дата и время создания задания. |
| `updated_at` | `TIMESTAMPTZ` | Дата и время последнего обновления задания. |

Основные правила:

- Задания можно создавать только если в `group_settings` включен `assignments_enabled`.
- `lesson_id`, если заполнен, должен ссылаться на урок той же группы.

### Таблица `assignment_files`

Связка между заданиями и вложенными файлами.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `assignment_id` | `UUID` | Ссылка на задание из таблицы `assignments`. |
| `file_id` | `UUID` | Ссылка на файл из таблицы `files`. |
| `sort_order` | `INTEGER` | Порядок файла внутри задания. |
| `attached_at` | `TIMESTAMPTZ` | Время прикрепления файла. |

Для таблицы `assignment_files` рекомендуется использовать составной первичный ключ `assignment_id + file_id`.

### Таблица `submissions`

Хранит попытки сдачи заданий пользователями.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `UUID` | Первичный ключ сдачи. |
| `assignment_id` | `UUID` | Ссылка на задание из таблицы `assignments`. |
| `author_id` | `UUID` | Пользователь, отправивший работу. |
| `attempt_number` | `INTEGER` | Порядковый номер попытки пользователя по конкретному заданию. |
| `text` | `TEXT` | Текстовое содержимое ответа. Может быть `NULL`. |
| `status` | `ENUM` | Статус сдачи: `DRAFT`, `SUBMITTED`, `REVIEWED`. |
| `score` | `INTEGER` | Балл по конкретной попытке. Может быть `NULL`. |
| `feedback` | `TEXT` | Комментарий проверяющего. Может быть `NULL`. |
| `submitted_at` | `TIMESTAMPTZ` | Время фактической отправки работы. Может быть `NULL`. |
| `reviewed_by_user_id` | `UUID` | Кто проверил работу. Может быть `NULL`. |
| `reviewed_at` | `TIMESTAMPTZ` | Когда работа была проверена. Может быть `NULL`. |
| `created_at` | `TIMESTAMPTZ` | Дата и время создания записи. |
| `updated_at` | `TIMESTAMPTZ` | Дата и время последнего обновления записи. |

Основные правила:

- Для одной пары `assignment_id + author_id` может существовать несколько попыток.
- Для пары `assignment_id + author_id + attempt_number` должна быть уникальность.
- Рекомендуется не допускать более одного черновика `DRAFT` для одной пары `assignment_id + author_id`.

### Таблица `submission_files`

Связка между попытками сдачи и прикрепленными файлами.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `submission_id` | `UUID` | Ссылка на сдачу из таблицы `submissions`. |
| `file_id` | `UUID` | Ссылка на файл из таблицы `files`. |
| `sort_order` | `INTEGER` | Порядок файла внутри сдачи. |
| `attached_at` | `TIMESTAMPTZ` | Время прикрепления файла. |

Для таблицы `submission_files` рекомендуется использовать составной первичный ключ `submission_id + file_id`.

## 5. Расписание

### Таблица `schedule_events`

Хранит самостоятельные события календаря группы, которые не являются уроками или дедлайнами заданий.

Уроки с заполненными `starts_at` и `ends_at`, а также задания с заполненным `due_at`, сами по себе участвуют в построении расписания и не должны дублироваться отдельными строками в `schedule_events`.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `UUID` | Первичный ключ события. |
| `group_id` | `UUID` | Группа, к которой относится событие. |
| `title` | `VARCHAR(200)` | Название события. |
| `description` | `TEXT` | Подробное описание события. Может быть `NULL`. |
| `starts_at` | `TIMESTAMPTZ` | Дата и время начала события. |
| `ends_at` | `TIMESTAMPTZ` | Дата и время окончания события. |
| `location` | `VARCHAR(255)` | Текстовое описание места или формата проведения. Может быть `NULL`. |
| `status` | `ENUM` | Статус события: `PLANNED`, `CANCELLED`. |
| `created_by_user_id` | `UUID` | Пользователь, создавший событие. |
| `cancelled_at` | `TIMESTAMPTZ` | Время отмены события. Может быть `NULL`. |
| `created_at` | `TIMESTAMPTZ` | Дата и время создания события. |
| `updated_at` | `TIMESTAMPTZ` | Дата и время последнего обновления события. |

Основные правила:

- События можно создавать только если в `group_settings` включен `schedule_enabled`.
- `schedule_events` используются только для отдельных событий, не дублирующих уроки и задания.

## 6. Чаты и сообщения

### Таблица `chats`

Единая таблица чатов. Поддерживает как групповые чаты, так и личные диалоги `1 на 1`.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `UUID` | Первичный ключ чата. |
| `chat_type` | `ENUM` | Тип чата: `GROUP`, `DIRECT`. |
| `group_id` | `UUID` | Ссылка на группу для группового чата. Для личного чата `NULL`. |
| `title` | `VARCHAR(150)` | Название группового чата. Для личного чата может быть `NULL`. |
| `direct_chat_key` | `VARCHAR(100)` | Нормализованный ключ пары пользователей для личного чата. Для группового чата `NULL`. |
| `created_by_user_id` | `UUID` | Пользователь, создавший чат. |
| `last_message_at` | `TIMESTAMPTZ` | Время последнего сообщения в чате. Может быть `NULL`. |
| `created_at` | `TIMESTAMPTZ` | Дата и время создания чата. |
| `updated_at` | `TIMESTAMPTZ` | Дата и время последнего обновления метаданных чата. |

Основные правила:

- Если `chat_type = GROUP`, поле `group_id` обязательно.
- Если `chat_type = DIRECT`, поле `group_id` должно быть `NULL`.
- Если `chat_type = DIRECT`, поле `direct_chat_key` обязательно и должно быть уникальным.
- Для личных чатов `direct_chat_key` строится из двух `user_id` в отсортированном порядке, чтобы не создавать дубликаты одного и того же диалога.

### Таблица `chat_members`

Хранит участников чатов и пользовательские данные участия.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `chat_id` | `UUID` | Ссылка на чат из таблицы `chats`. |
| `user_id` | `UUID` | Ссылка на пользователя из таблицы `users`. |
| `joined_at` | `TIMESTAMPTZ` | Дата и время вступления пользователя в чат. |
| `last_read_at` | `TIMESTAMPTZ` | До какого времени пользователь прочитал сообщения в чате. Может быть `NULL`. |
| `created_at` | `TIMESTAMPTZ` | Дата и время создания строки участия. |
| `updated_at` | `TIMESTAMPTZ` | Дата и время последнего обновления данных участия. |

Для таблицы `chat_members` используется составной первичный ключ `chat_id + user_id`.

Основные правила:

- У личного чата должно быть ровно два участника.
- У группового чата участников может быть много.
- Для личных чатов строки в `chat_members` создаются сразу для обоих пользователей.

### Таблица `messages`

Хранит сообщения внутри чатов.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `UUID` | Первичный ключ сообщения. |
| `chat_id` | `UUID` | Ссылка на чат из таблицы `chats`. |
| `author_id` | `UUID` | Пользователь, отправивший сообщение. |
| `text` | `TEXT` | Текст сообщения. Может быть `NULL`, если сообщение состоит только из файлов. |
| `edited_at` | `TIMESTAMPTZ` | Время последнего редактирования сообщения. Может быть `NULL`. |
| `deleted_at` | `TIMESTAMPTZ` | Время мягкого удаления сообщения. Может быть `NULL`. |
| `created_at` | `TIMESTAMPTZ` | Дата и время отправки сообщения. |

Основные правила:

- У сообщения должен быть либо текст, либо хотя бы одно вложение.
- При создании сообщения следует обновлять `chats.last_message_at`.
- Для истории переписки используется мягкое удаление через `deleted_at`.

### Таблица `message_files`

Связка между сообщениями и прикрепленными файлами.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `message_id` | `UUID` | Ссылка на сообщение из таблицы `messages`. |
| `file_id` | `UUID` | Ссылка на файл из таблицы `files`. |
| `sort_order` | `INTEGER` | Порядок файла внутри сообщения. |
| `attached_at` | `TIMESTAMPTZ` | Время прикрепления файла. |

Для таблицы `message_files` рекомендуется использовать составной первичный ключ `message_id + file_id`.

## 7. Основные enum-значения

Ниже перечислены ключевые enum-значения, которые уже зафиксированы в модели.

- `groups.access_mode`: `OPEN`, `BY_REQUEST`, `CLOSED`
- `groups.status`: `ACTIVE`, `ARCHIVED`, `DELETED`
- `group_members.role`: `OWNER`, `ADMIN`, `USER`
- `group_join_requests.status`: `PENDING`, `APPROVED`, `REJECTED`
- `lessons.status`: `DRAFT`, `PUBLISHED`, `ARCHIVED`
- `assignments.status`: `DRAFT`, `PUBLISHED`, `ARCHIVED`
- `submissions.status`: `DRAFT`, `SUBMITTED`, `REVIEWED`
- `schedule_events.status`: `PLANNED`, `CANCELLED`
- `chats.chat_type`: `GROUP`, `DIRECT`

## 8. Основные связи между сущностями

- Один пользователь может иметь много сессий через связь `users -> sessions`.
- Один пользователь может загружать много файлов через связь `users -> files`.
- Один пользователь может владеть многими группами через связь `users -> groups.owner_id`.
- Одна группа имеет ровно одну строку настроек через связь `groups -> group_settings`.
- Один пользователь может состоять во многих группах через таблицу `group_members`.
- Для группы с режимом `BY_REQUEST` пользователи подают заявки через `group_join_requests`.
- Одна группа может содержать много уроков, заданий, событий расписания и групповых чатов.
- Один урок может иметь много файлов через `lesson_files`.
- Одно задание может быть связано с одним уроком, но урок может содержать несколько заданий.
- Одно задание может иметь много файлов через `assignment_files`.
- Одно задание может иметь много попыток сдачи от пользователей через `submissions`.
- Одна сдача может иметь много файлов через `submission_files`.
- Один чат может содержать много участников через `chat_members`.
- Один чат может содержать много сообщений через `messages`.
- Одно сообщение может иметь много файлов через `message_files`.

## 9. Вывод

Новая структура базы данных покрывает текущий `MVP` SmartTeach: пользователей и авторизацию, группы и заявки на вступление, настройку функций группы, учебные сущности, расписание, групповые и личные чаты, а также универсальную работу с файлами.

Схема остается достаточно простой для первой рабочей версии, но при этом уже подготовлена к дальнейшему росту проекта: в ней есть отдельная таблица настроек группы, поддержка нескольких попыток сдачи, мягкое удаление ключевых сущностей и единая модель хранения вложений.
