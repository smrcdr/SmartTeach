# Спека: реальный frontend MVP для SmartTeach

## Цель

Собрать полноценный рабочий frontend для SmartTeach на базе текущего backend API, а не на базе старых моков и устаревших docs.

Frontend должен стать продуктовым приложением для работы с группами, уроками, заданиями, расписанием и чатами. Текущие `.vue`-экраны можно использовать только как очень грубый визуальный референс, но не как источник поведения, данных или структуры.

## Источник истины

Приоритет источников:

1. `apps/web/public/openapi.yml`
2. текущая backend-реализация в `apps/api/src/modules/**`
3. договорённости из discovery по этому frontend
4. старые docs только как вторичный контекст

Старые docs больше не считаются источником истины в частях про `course/class`, `OAuth`, глобальные роли сервиса, админку и уведомления.

## Продуктовая рамка MVP

### Основная модель

- В продукте есть только сущность `group`.
- Отдельных сущностей `course` и `class` в MVP нет.
- Приложение `auth-first`: публичны только лендинг, вход и регистрация.
- После логина пользователь попадает в `Мои группы`.
- Отдельного глобального дашборда после логина нет.

### Внутри группы

- У каждой группы есть единый `workspace`.
- На desktop у workspace есть локальный `sidebar`.
- На mobile локальная навигация группы открывается через кнопку `Разделы группы` и `sheet/drawer`.
- Базовые разделы workspace:
  - `Обзор`
  - `Уроки`
  - `Задания`
  - `Расписание`
  - `Чаты`
  - `Участники`
  - `Заявки` только для `BY_REQUEST` и только для `OWNER/ADMIN`
  - `Настройки` только для `OWNER/ADMIN`
- Отключённые модули скрываются из навигации.

### Глобальная структура приложения

- После авторизации используется постоянный `app-shell`.
- Глобальная навигация на desktop: верхний `topbar`.
- Глобальная навигация на mobile: `topbar + hamburger menu`.
- Основные глобальные разделы:
  - `Группы`
  - `Чаты`
  - `Профиль` через avatar-menu
- Справа в topbar есть CTA `Создать группу`.
- В topbar есть глобальный поиск только по группам.
- Глобальный поиск всегда ведёт в `Группы -> Все` с применённым поисковым запросом.

## Scope MVP

### Входит в MVP

- публичный компактный лендинг
- отдельные страницы `Вход` и `Регистрация`
- cookie-based auth flow с silent refresh
- раздел `Группы` с вкладками `Мои` и `Все`
- создание группы
- вступление в группу через каталог и через код
- preview группы для не-участника
- group workspace со всеми agreed-модулями
- CRUD уроков
- CRUD заданий
- submission flow с черновиками, несколькими попытками, проверкой и feedback
- agenda-расписание с кастомными событиями
- глобальные и локальные чаты
- участники, роли, заявки, передача владения
- настройки группы, архивирование, восстановление, leave flow
- профиль текущего пользователя
- публичный минимальный профиль другого пользователя
- загрузка файлов везде, где backend уже готов

### Не входит в MVP

- `OAuth`
- глобальные роли сервиса (`ADMIN`, `MODERATOR`)
- административная панель сервиса
- уведомления
- dark mode
- глобальный дашборд после логина
- поиск по сообщениям
- presence, typing, unread counters
- публичный каталог `CLOSED`-групп
- ручное добавление участников в `CLOSED`-группы
- отдельная сущность `course/class`

## Ключевые продуктовые решения

### Группы

- Раздел `Группы` имеет один общий layout с вкладками `Мои / Все`.
- `Мои` — рабочий список.
- `Все` — каталог.
- В обеих вкладках используются карточки.
- Во вкладке `Мои`:
  - фильтры: поиск + `Активные / Архив`
  - карточка показывает название, описание, мою роль, число участников, включённые модули
- Во вкладке `Все`:
  - фильтры: поиск + `accessMode`
  - карточка показывает название, описание, владельца, число участников, режим доступа, включённые модули
  - если пользователь уже состоит в группе, карточка остаётся в каталоге и ведёт в workspace
- Если у нового пользователя нет групп, во вкладке `Мои` показывается сильный empty state с CTA:
  - `Создать группу`
  - `Найти группу`
  - `Ввести код`

### Вступление в группу

- Основной сценарий вступления: через вкладку `Все`.
- Дополнительный сценарий: отдельный экран/flow `Ввести код`.
- Для не-участника открывается отдельная `preview`-страница группы.
- `OPEN`: кнопка `Вступить`.
- `BY_REQUEST`: кнопка `Подать заявку`, затем состояние `Заявка отправлена`.
- `CLOSED`: не показывается outsider’ам вообще, так как текущий backend скрывает такие группы.

### Создание группы

- Создание группы — одна полноценная форма на одном экране.
- Дефолты:
  - `accessMode = OPEN`
  - `chatEnabled = true`
  - `lessonsEnabled = false`
  - `assignmentsEnabled = false`
  - `scheduleEnabled = false`

### Обзор группы

- `Обзор` — операционная сводка, а не декоративная страница.
- На странице показываются:
  - название и описание
  - код группы
  - владелец
  - число участников
  - включённые модули
  - ближайшие уроки, дедлайны и события
  - быстрые переходы в разделы группы

### Уроки

- Уроки существуют как отдельный модуль группы.
- Урок может быть:
  - без даты вообще
  - только с `startsAt`
  - с `startsAt + endsAt`
- Основной список уроков строится по ручному порядку (`sortOrder`), а дата показывается как метаданные.
- Для `OWNER/ADMIN`:
  - full CRUD
  - фильтры по статусу
  - визуальное переупорядочивание списка
  - create/edit через отдельные full-page формы
  - явные действия `Сохранить черновик` и `Опубликовать`
  - `Архивировать` как отдельное вторичное действие после создания
- Экран урока — операционный:
  - содержимое
  - attached files
  - связанные задания

### Задания

- Задания могут быть:
  - связанными с уроком
  - самостоятельными внутри группы
- Основной список заданий:
  - задания с дедлайном идут первыми по сроку
  - задания без дедлайна идут ниже
  - связь с уроком показывается как метаданные
- `dueAt` опционален.
- `maxScore` опционален.
- Для `OWNER/ADMIN`:
  - full CRUD
  - фильтры по статусу
  - create/edit через отдельные full-page формы
  - явные действия `Сохранить черновик` и `Опубликовать`
  - `Архивировать` как отдельное вторичное действие после создания
- Экран задания для `USER`:
  - условие и метаданные
  - `Моя текущая работа`
  - история прошлых попыток
- Экран задания для `OWNER/ADMIN`:
  - двухпанельный admin view
  - задание и метаданные
  - справа список submission’ов
  - submission’ы группируются по участникам
  - основной review flow работает с последней попыткой

### Submission flow

- У пользователя может быть один `DRAFT` на задание.
- На форме есть явные действия:
  - `Сохранить черновик`
  - `Отправить`
- После `SUBMITTED` или `REVIEWED` пользователь может начать новую попытку.
- Предыдущие попытки остаются в истории.
- Если у задания нет `maxScore`, review работает только через `feedback`.

### Расписание

- Основной экран расписания — `agenda / лента по дням`.
- В ленте смешиваются:
  - уроки
  - дедлайны заданий
  - кастомные события
- Для `OWNER/ADMIN` есть full CRUD кастомных событий.
- По умолчанию используются быстрые фильтры по типам событий:
  - `Уроки`
  - `Дедлайны`
  - `События`
  - по умолчанию включены все

### Чаты

- Есть глобальный экран `Чаты` и локальный чат-контекст внутри группы.
- Внутри группы раздел `Чаты` остаётся частью group workspace.
- Глобальный экран `Чаты` — `direct-first` и имеет вкладки:
  - `Личные`
  - `Групповые`
- На desktop chat layout — `split view`:
  - слева список чатов/комнат
  - справа активный диалог
- На mobile: сначала список, затем отдельный экран диалога
- Список чатов/комнат в левой панели:
  - название
  - preview последнего сообщения
  - время последней активности
  - аватар или иконка
- Если у группы включён chat-модуль, но комнат нет:
  - `OWNER/ADMIN` видят CTA `Создать первый чат`
  - участники видят честный empty state
- Создание группового чата — через простую модалку.
- История сообщений догружается через кнопку `Загрузить предыдущие`.
- Удалённые сообщения остаются в ленте как плейсхолдер `Сообщение удалено`.
- Автор может редактировать и удалять свои сообщения.
- `OWNER/ADMIN` могут удалять чужие сообщения в групповых чатах.
- В MVP отсутствуют:
  - поиск по сообщениям
  - unread
  - online/presence
  - typing

### Участники, роли, заявки

- Все участники видят состав группы.
- `OWNER/ADMIN` могут:
  - менять роли
  - удалять участников
  - рассматривать заявки
- Для `BY_REQUEST` есть отдельный пункт `Заявки` в sidebar группы.
- В UI нужен явный flow передачи владения группой.
- Стандартный `leave group` доступен через UI для `USER` и `ADMIN`.
- `OWNER` вместо выхода получает сценарий передачи владения.

### Настройки группы

- `OWNER/ADMIN` могут менять:
  - `name`
  - `description`
  - `accessMode`
  - `status`
  - feature toggles
- При выключении модуля нужен confirm-step с явным предупреждением:
  - данные не удаляются
  - раздел исчезает из навигации
  - участники теряют к нему доступ
- Архивная группа открывается как полностью read-only workspace.
- `OWNER/ADMIN` могут архивировать и восстанавливать группу.
- Мягкое удаление группы через UI доступно только `OWNER`.

### Профиль

- Профиль текущего пользователя ограничен API-полями:
  - `displayName`
  - `bio`
  - `avatar`
- Публичный профиль другого пользователя минимальный:
  - аватар
  - имя
  - bio
  - CTA `Написать`

## Роли и видимость

- `USER` видит только `PUBLISHED` уроки и задания.
- `OWNER/ADMIN` видят `DRAFT`, `PUBLISHED`, `ARCHIVED`.
- Архивные группы доступны для просмотра, но не для записи.
- `DELETED`-группы в UI не показываются.
- `CLOSED`-группы не показываются outsider’ам.
- Direct chat создаётся только из пользовательского контекста:
  - участники
  - профиль пользователя
  - автор submission
  - другие аналогичные места, где уже известен `userId`

### Контрактные ограничения, которые frontend принимает

- У большинства списков нет полноценной пагинации. Для MVP считаем объёмы умеренными и грузим такие списки целиком.
- Пагинация сообщений уже есть и используется через `limit + before`.
- Поиск групп реализуется только через `search` и `accessMode`.
- Отдельного global user search нет.
- Поиск по сообщениям отсутствует.

## Backend gaps и обязательные изменения контракта

### 1. Refresh token в `httpOnly cookie`

Это ключевое отличие от текущего `openapi.yml`.

Требуемое целевое поведение:

- `login/register` выставляют `refreshToken` в `httpOnly cookie`
- frontend хранит `accessToken` только в памяти
- `/auth/refresh` работает по cookie и возвращает новый `accessToken`
- `/auth/logout` очищает cookie

Следствия:

- нужно обновить backend auth-контракт
- нужно обновить `openapi.yml`
- нужно заново сгенерировать frontend API client

### 2. OpenAPI должен быть синхронизирован с backend после auth-изменений

До начала фронтенд-реализации auth-слоя нужен актуальный `openapi.yml`, иначе codegen будет строиться на ложном контракте.

## Дизайн и UX-направление

- Вся авторизованная часть — сдержанный `product workspace`.
- Лендинг визуально близок к продукту, без ярко выраженного маркетингового стиля.
- Только светлая тема.
- Desktop-first, но все основные потоки должны оставаться рабочими на mobile.
- Старые `.vue`-экраны не копировать один в один.
- Нельзя переносить в новый UI старые поля и сценарии, которых нет в API.

## Frontend-архитектура

### Базовый стек

- `Vue 3`
- `Vue Router`
- `TanStack Query`
- `Pinia` только для небольшого client state
- codegen API client из `apps/web/public/openapi.yml`

### Предлагаемая структура кода

```text
apps/web/src/
  app/
  router/
  layouts/
  shared/
    api/
      generated/
      client/
    ui/
    lib/
  features/
    auth/
    groups/
    lessons/
    assignments/
    submissions/
    schedule/
    chats/
    profile/
  pages/
```

### Состояние

- Серверное состояние живёт в query/mutation-слое.
- Pinia используется только для:
  - auth-session state
  - небольшого UI state
  - возможно, websocket/chat session coordination, если это не покрывается composables
- Route guards отвечают за:
  - требование auth
  - разделение public/private routes
  - недопуск outsider’а в group workspace

### Async-поведение

- При `401` выполняется silent refresh.
- После успешного refresh исходный запрос повторяется.
- Если refresh не удался, пользователь переводится на страницу `Вход`.
- Для всех мутаций нужны явные loading/error/success states.
- Для списков и экранов нужны честные:
  - loading states
  - empty states
  - error states

### Files

- Upload UI нужен для:
  - аватара
  - файлов урока
  - файлов задания
  - файлов submission
  - вложений сообщений
- Прикрепление файлов должно идти только через реальный `/files` flow, без локальных фиктивных вложений.

### Realtime

- Realtime нужен только для чатов.
- WebSocket интеграция изолируется внутри chat-модуля.
- События чатов должны обновлять query cache без полной перезагрузки страницы.

## Тестирование и проверка

Минимальные ожидания для этапа реализации:

- `npm run build` должен проходить для всего репозитория
- `npm run build:web` должен проходить отдельно
- ручная проверка ключевых сценариев:
  - login/register/logout
  - silent refresh
  - `Мои / Все группы`
  - создание группы
  - join/open/by-request flow
  - preview группы
  - group workspace
  - уроки
  - задания и submission flow
  - расписание
  - чаты
  - участники / заявки / настройки
  - профиль

## Acceptance criteria

- Старый frontend больше не опирается на mock-данные как на основную модель приложения.
- Все основные экраны соответствуют реальному backend API.
- Авторизованная часть собрана вокруг единого `app-shell`.
- Группы, group workspace, уроки, задания, submissions, расписание, чаты, участники и настройки реализованы в рамках agreed scope.
- UI не содержит устаревших сущностей `course/class` и не показывает полей, которых нет в API.
- Auth flow соответствует новому cookie-based refresh контракту.
- Архивные, preview и permission-driven состояния обрабатываются честно.
- Мобильная адаптация покрывает базовые рабочие сценарии.

## Кандидатный план реализации

### Фаза 0. Подготовка контракта

- Обновить backend auth на `httpOnly cookie refresh flow`
- Обновить `openapi.yml`
- Выбрать codegen-инструмент
- Сгенерировать типизированный API client

### Фаза 1. Frontend foundation

- Пересобрать структуру `apps/web`
- Подключить `TanStack Query` и `Pinia`
- Собрать router и route guards
- Собрать базовый `app-shell`
- Вынести базовые UI primitives и layout-компоненты

### Фаза 2. Публичная зона и auth

- Лендинг
